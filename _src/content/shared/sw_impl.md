## 통합 구현과 개발 환경

**통합 구현**은 모듈을 결합해 하나의 시스템으로 완성하는 과정이다. 구성 요소: **송신 시스템, 수신 시스템, 중계 시스템, 연계 데이터, 네트워크**.

| 개발 환경 | 예 |
|---|---|
| 하드웨어 | 클라이언트, 웹 서버(정적 — Apache, Nginx), WAS(동적 — Tomcat, JEUS), DB 서버, 파일 서버 |
| 소프트웨어 | 운영체제, JVM, 웹 서버, WAS, DBMS |
| 개발 도구 | IDE(이클립스, IntelliJ, VS Code), 빌드 도구(**Ant, Maven, Gradle**), 형상관리 도구, 테스트 도구(JUnit) |

**빌드 도구**: 소스를 컴파일·패키징해 실행 가능한 산출물을 만든다. Ant(XML, 초기), **Maven**(pom.xml, 의존성 관리), **Gradle**(Groovy/Kotlin DSL, 안드로이드 기본), Jenkins(CI 서버).

## 제품 소프트웨어 패키징

사용자 중심으로 실행 파일·매뉴얼·설치 도구를 묶어 배포하는 것. 신규·변경 개발 소스를 식별하고 **모듈화**하여 패키징한다.

| 고려 사항 | 설명 |
|---|---|
| 사용자 실행 환경 | OS, CPU, 메모리 등 최소 환경 정의 |
| UI | 사용자가 시각적으로 이해하기 쉽게 |
| 관리 서비스 | 지속적 업데이트 |
| 보안 | DRM(디지털 저작권 관리) — 암호화, 키 관리, 식별 기술, 저작권 표현, 정책 관리, 크랙 방지, 인증 |

**DRM 구성 요소**: 콘텐츠 제공자, 콘텐츠 분배자, 패키저(콘텐츠를 메타데이터와 함께 배포 단위로 묶음), 보안 컨테이너, DRM 컨트롤러, 클리어링 하우스(사용 권한·라이선스 발급, 결제 관리), 콘텐츠 소비자.

**매뉴얼**: 설치 매뉴얼(설치 과정, 환경, 삭제 방법), 사용자 매뉴얼(기능·사용법, 고객 지원). 국제 표준 **ISO/IEC 25000**(SQuaRE — 소프트웨어 품질 평가 통합 모델), ISO/IEC 9126(품질 특성), ISO/IEC 12119, 14598.

## 형상 관리와 버전 관리

**형상 관리(SCM)**는 소프트웨어 변경 사항을 체계적으로 관리하는 활동이다.

| 절차 | 설명 |
|---|---|
| 형상 식별 | 관리 대상을 정하고 이름·번호 부여 |
| 형상 통제 | 변경 요청을 검토·승인해 **기준선(Baseline)**에 반영. 형상 통제 위원회(CCB) |
| 형상 감사 | 기준선 변경이 제대로 되었는지 검토 |
| 형상 기록(상태 보고) | 변경 내용을 기록·보고 |

| 버전 관리 도구 | 방식 | 특징 |
|---|---|---|
| RCS | 로컬 | 파일 잠금, 한 명만 수정 |
| CVS | 중앙 집중 | 서버-클라이언트 |
| **SVN (Subversion)** | 중앙 집중 | CVS 개선. commit, update, checkout, trunk/branches/tags |
| **Git** | **분산** | 로컬 저장소에서 작업 후 원격에 push. 리누스 토르발스 개발 |
| Bitkeeper | 분산 | |

| Git 명령 | 기능 |
|---|---|
| `git init` / `git clone` | 저장소 생성 / 복제 |
| `git add` | 스테이징 영역에 추가 |
| `git commit -m` | 로컬 저장소에 기록 |
| `git push` / `git pull` | 원격으로 올리기 / 원격에서 가져와 병합 |
| `git fetch` | 원격 변경 사항만 가져옴(병합 안 함) |
| `git branch` / `git checkout` (switch) | 브랜치 생성 / 전환 |

| `git status` / `git log` | 상태 / 이력 |

## 애플리케이션 테스트

### 테스트 원리

1. 테스트는 결함이 **존재함**을 밝히는 것이지, 결함이 없음을 증명하지 못한다
2. **완벽한 테스트는 불가능**하다
3. 개발 초기에 테스트를 시작해야 한다
4. **결함 집중**: 적은 수의 모듈에 대부분의 결함이 몰린다 (**파레토 법칙** 80:20)
5. **살충제 패러독스**: 같은 테스트를 반복하면 새 결함을 찾지 못한다 → 테스트 케이스를 계속 보완
6. 테스트는 정황(context)에 의존한다
7. **오류-부재의 궤변**: 결함이 없어도 사용자 요구를 만족하지 못하면 품질이 높다고 할 수 없다

| 구분 | 검증 (Verification) | 확인 (Validation) |
|---|---|---|
| 질문 | 제품을 **올바르게** 만들고 있는가? (명세서대로) | **올바른 제품**을 만들고 있는가? (사용자 요구대로) |
| 관점 | 개발자 | 사용자 |

### 화이트박스 테스트 (구조 기반)

소스 코드의 내부 논리를 보고 테스트한다.

| 기법 | 설명 |
|---|---|
| 기초 경로 검사 | 맥케이브의 순환 복잡도로 독립 경로를 테스트 |
| 제어 구조 검사 | 조건 검사, 루프 검사, 데이터 흐름 검사 |

**순환 복잡도(Cyclomatic Complexity)** V(G) = **E − N + 2** (E: 간선 수, N: 노드 수) = 판단(조건) 노드 수 + 1 = 영역 수.

| 커버리지 | 기준 |
|---|---|
| 구문(문장) 커버리지 | 모든 **문장**을 한 번 이상 실행 |
| 결정(분기) 커버리지 | 모든 **결정문**의 참·거짓을 한 번 이상 |
| 조건 커버리지 | 결정문 안 각 **개별 조건**의 참·거짓을 한 번 이상 |
| 조건/결정 커버리지 | 결정 + 조건 모두 |
| 변경 조건/결정 (MC/DC) | 각 개별 조건이 결정 결과에 독립적으로 영향을 주는지 |
| 다중 조건 커버리지 | 모든 조건 **조합** |

### 블랙박스 테스트 (명세 기반)

내부 구조를 보지 않고 입력과 출력만으로 테스트한다.

| 기법 | 설명 |
|---|---|
| 동등 분할 (Equivalence Partitioning) | 입력값을 유효·무효 그룹으로 나눠 대표값 테스트 |
| 경계값 분석 (Boundary Value) | 경계 부근 값(최솟값−1, 최솟값, 최댓값, 최댓값+1) 테스트. 오류가 경계에서 자주 발생 |
| 원인-효과 그래프 | 입력과 출력의 관계를 그래프로 분석 |
| 오류 예측 | 경험으로 오류를 예측 |
| 비교 검사 | 여러 버전에 같은 입력을 넣어 비교 |
| 결정 테이블, 상태 전이, 유스케이스, 페어와이즈 | |

:::ex 경계값 분석
점수 0~100 입력: −1, 0, 100, 101 (또는 −1, 0, 1, 99, 100, 101)
동등 분할: 90 이상 A, 80~89 B … 각 구간에서 대표값 하나씩
:::

### 테스트 레벨과 V 모델

| 개발 단계 | ↔ | 테스트 레벨 | 내용 |
|---|---|---|---|
| 요구사항 분석 | ↔ | **인수 테스트** | 사용자가 요구를 만족하는지. 알파 테스트(개발자 앞에서 사용자가), 베타 테스트(사용자 환경에서) |
| 분석 | ↔ | **시스템 테스트** | 전체 시스템이 기능·비기능 요구를 만족하는지 |
| 설계 | ↔ | **통합 테스트** | 모듈 간 인터페이스 |
| 구현(코딩) | ↔ | **단위 테스트** | 개별 모듈 (화이트박스 위주) |

### 통합 테스트 방식

| 방식 | 설명 | 필요한 가짜 모듈 |
|---|---|---|
| 하향식 (Top-Down) | 상위 모듈부터 아래로. 깊이 우선·너비 우선 | **스텁(Stub)**: 아직 없는 **하위** 모듈 대신 |
| 상향식 (Bottom-Up) | 하위 모듈을 묶은 **클러스터**부터 위로 | **드라이버(Driver)**: 아직 없는 **상위** 모듈 대신 |
| 빅뱅 | 모든 모듈을 한꺼번에 | 없음 |
| 샌드위치 | 상향 + 하향 | 둘 다 |

- **회귀 테스트**: 수정 후 다른 곳에 새 오류가 생기지 않았는지 다시 테스트
- **테스트 오라클**: 테스트 결과가 맞는지 판단하는 기준. 참(True) 오라클, 샘플링 오라클, 추정(휴리스틱) 오라클, 일관성 검사 오라클
- **테스트 하네스**: 테스트 드라이버, 스텁, 테스트 슈트, 테스트 케이스, 테스트 스크립트, 목 오브젝트
- **테스트 케이스** 구성: 식별자, 테스트 항목, 입력값, 예상 결과, 실행 조건

### 결함 관리와 성능

**결함 관리 프로세스**: 관리 계획 → 결함 기록 → 검토 → 수정 → 재확인 → 결함 상태 추적 → 최종 분석.

| 성능 지표 | 의미 |
|---|---|
| 처리량 (Throughput) | 단위 시간당 처리 건수 |
| 응답 시간 (Response Time) | 요청 후 첫 응답까지 |
| 경과 시간 (Turnaround Time) | 요청 후 처리 완료까지 |
| 자원 사용률 | CPU·메모리·네트워크 사용률 |

**소스 코드 품질 분석**: 정적 분석(실행하지 않고 코드 분석 — PMD, Cppcheck, SonarQube, Checkstyle), 동적 분석(실행하며 분석 — Avalanche, Valgrind). **리팩토링**: 기능은 그대로 두고 코드 구조를 개선. **나쁜 코드**: 스파게티 코드, 외계인 코드(오래되어 아무도 모름). **클린 코드** 원칙: 가독성, 단순성, 의존성 최소, 중복성 제거, 추상화.

**애플리케이션 성능 개선**: 코드 최적화, 알고리즘 개선, 정규화·인덱스, 캐시.
